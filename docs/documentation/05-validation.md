# Процедура валидации и результаты {#validation}

Готовых датасетов и эталонной разметки ТЗ не даёт, поэтому качество механик проверяется на **синтетических данных с известной истиной**. Генератор задаёт скрытые атрибуты: истинный уровень, навыки, отрасль. Платформа видит только зашумлённые наблюдения, как в продукте. Эталон считается только по скрытым атрибутам, так что система не может подсмотреть ответ. Все прогоны детерминированы и воспроизводятся одной командой:

```sh
cd apps/api
gradle validateAssessment   # → docs/validation/assessment-results.{md,json}
gradle validateMatching     # → docs/validation/matching-results.{md,json}, matching-pairs.csv
```

Полные отчёты с методикой, таблицами по специализациям и потребностям, абляциями и чувствительностью лежат в `docs/validation/`. Ниже — сводка.

## Тестирование

**Модель.** 10 000 синтетических кандидатов (по 2 000 на специализацию), истинный уровень θ ~ N(0, 1). Эталонный грейд — полоса θ по тем же порогам. Самооценка кандидата зашумлена и в среднем завышена. Ответы генерируются по 3PL с параметрами семейства, но трудность каждого экземпляра смещена на δ ~ N(0; 0.25²), то есть изоморфность неидеальна. Движок о δ не знает. Каждый кандидат проходит весь путь дважды на независимых экземплярах. Симуляция вызывает те же объекты, что и API: генераторы, blueprint, CAT, EAP, правила грейда и пересдачи. Для сравнения тот же набор кандидатов прогнан через прежний механизм: 5 случайных вопросов из банка в 25 штук, грейд по доле верных.

| Критерий жюри | Метрика | Новый механизм | Прежний |
|---|---|---|---|
| Соответствие эталону | точность грейда | **78.6%** | 27.2% |
| Соответствие эталону | macro-F1 | **0.78** | 0.23 |
| Корректность категоризации | доля завышенных грейдов | **6.5%** | 71.8% |
| Согласованность | взвешенная каппа при повторе на других экземплярах | **0.71** | 0.17 |
| Согласованность | корреляция оценок двух прохождений | **0.77** | 0.23 |
| Дискриминативность | корреляция оценки с истинным θ | **0.87** | 0.46 |
| Дискриминативность | средняя item–rest корреляция семейств | **0.37** | — |
| Устойчивость к утечкам | доля идентичных заданий у двух кандидатов | **1.9%** | 68.1% |
| Устойчивость к утечкам | эффект от выученной утечки 1 000 показанных вопросов | **+5.7 балла** (завышение 7.5% → 13.9%) | весь банк: 100 баллов и senior у всех |

Надёжность теста — 0.76, средняя SE — 0.48. Одно семейство с item–rest ниже 0.20 помечено на доработку. **Слабые места** отчёт показывает честно: наибольший выигрыш от утечки дают концептуальные семейства с вариантами, особенно в дизайне (+8.4 балла при утечке 1 000) и продукте (+7.0). Их расширяем и ротируем в первую очередь. Порог k = 0, длина теста 12 и правило выбора заданий выбраны перебором; результаты устойчивы к разбросу трудности экземпляров от 0 до 0.5.

## Подбор

**Тестовый набор пар «вакансия – кандидат».** Пять независимых синтетических рынков по 360 кандидатов и 24 потребности работодателей, написанные как русские описания вакансий. Пять специализаций, три грейда, девять отраслей. Наблюдения зашумлены: тест ошибается на ступень с вероятностью 0.15; 30% кандидатов добавляют в стек 1–2 выдуманных навыка, 20% — «накрутчики» с 4–6 навыками; 25% завышают самооценку грейда; история ФСП есть лишь у части кандидатов. Эталонная релевантность 0–3 считается по скрытой истине (уровень, покрытие стека, отрасль). Её формула **намеренно отличается** от формулы движка. Метрики P@k, nDCG@10 и MRR усреднены по 120 парам «потребность × рынок», 95% доверительные интервалы — бутстрэпом. Веса задавались заранее, без подгонки. Набор пар с метками лежит в `docs/validation/matching-pairs.csv`, так что жюри может перепроверить.

| Система | P@5 | P@10 | nDCG@10 | MRR |
|---|---|---|---|---|
| **Подбор под потребность (платформа)** | **0.74** | **0.62** | **0.709** [0.685–0.731] | **0.919** |
| Категория + сила профиля (режим банка) | 0.65 | 0.57 | 0.612 | 0.840 |
| Только балл теста | 0.55 | 0.50 | 0.549 | 0.711 |
| Ключевые слова + заявленный стек («как на обычных площадках») | 0.41 | 0.37 | 0.433 | 0.648 |
| Случайный порядок внутри категории | 0.42 | 0.42 | 0.447 | 0.623 |
| Случайный порядок по специализации | 0.19 | 0.19 | 0.216 | 0.390 |

- Движок превосходит поиск по ключевым словам на **+0.276 nDCG@10** [0.246; 0.306].
- Учёт описания потребности (текст, стек, отрасль) даёт +0.13 nDCG@10, а отказ от результатов теста стоит −0.06.
- «Накрутчики» стека занимают 51% топ-10 у поиска по ключевым словам и 23% у движка при доле в пуле 20%.
- Изменение любого веса ×0.5 или ×1.5 оставляет nDCG@10 в диапазоне 0.636–0.732: ранжирование не держится на тонкой настройке.
- Исключение фактора ФСП на синтетике чуть улучшает метрику (+0.013). Генератор считает ФСП слабым сигналом, а вес оставлен, потому что ТЗ требует поднимать подтверждённые достижения. Это отражено в отчёте.

## Функциональная проверка

- **Автотесты API:** 96 тестов (`gradle test`), включая HTTP-сценарии на настоящем Ktor-модуле с подписанными RSA-токенами через JWKS. Покрыты:
  - выбор роли;
  - тест (провал senior → доступен только middle → успех → блокировки → истечение);
  - подбор, банк, карточка, приватность, привязка ФСП;
  - вакансии, отклики и раскрытие контактов, еженедельные задания;
  - коды 400, 401, 403, 404 и 409.
- **Миграции** проверяются на PostgreSQL 16, в том числе поверх базы с данными (V1 → V7).
- **Smoke-проверки:** `docs/smoke_*.py` для локального стенда; `docs/smoke_demo.py` для развёрнутого стенда (вход через форму Keycloak и PKCE, подборка с объяснениями, правило раскрытия контактов, приглашение кандидату).
- **Фронтенд:** `svelte-check` без ошибок, production-сборка, Prettier.

## Ограничения и план валидации на реальных данных

Результаты получены на синтетике с экспертными параметрами. Это проверка того, что механика восстанавливает заданную истину по зашумлённым сигналам, а не доказательство качества найма. План:

1. **Пилот теста.** Не меньше 200–300 ответов на семейство; калибровка 2PL/3PL (marginal ML), проверка согласия, одномерности и DIF по отраслям. Модель со случайным эффектом экземпляра, чтобы измерить реальную неизоморфность.
2. **Экспертный эталон.** 60–100 добровольцев, независимое структурированное интервью двумя экспертами вслепую, сравнение с грейдом теста (точность, взвешенная каппа), при необходимости — сдвиг порогов.
3. **Подбор.** Работодатели-эксперты размечают релевантность кандидатов по реальным потребностям, включая не попавших в выдачу. Метрики P@k и nDCG@k с базовыми линиями. Затем A/B-тест на доле принятых приглашений.
4. **Мониторинг.** Контрольные карты доли верных ответов при фиксированном θ (признак утечки), ротация вариантов, версия движка в каждой попытке.
