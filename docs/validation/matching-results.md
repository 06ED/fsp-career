# Валидация механики подбора: синтетический набор пар «вакансия – кандидат»

> Файл сгенерирован командой `cd apps/api && gradle validateMatching` (детерминированно, без сети и БД). 
> **Метки эталона синтетические**: они вычислены из скрытых атрибутов сгенерированных кандидатов, а не поставлены экспертами. 
> Это проверка того, что ранжирование восстанавливает заранее заданную «истину» по зашумлённым наблюдаемым сигналам, а не доказательство качества найма на реальном рынке.

## Ключевые результаты

- Доля релевантных кандидатов в топ-10 (P@10): **0,63** у движка против 0,37 у поиска по ключевым словам и заявленному стеку и 0,19 у случайного порядка.
- nDCG@10: **0,712** (95 % ДИ 0,688–0,734); разница с ключевыми словами +0,278 [0,249; 0,308].
- Режим банка (только подтверждённый профиль в точной категории) уже даёт nDCG@10 0,612; учёт описания потребности добавляет +0,099 [0,075; 0,125].
- Без описания потребности (TF-IDF-текст + стек + отрасль) nDCG@10 падает на 0,136 [0,111; 0,162]; по отдельности текст и стек частично взаимозаменяемы (см. абляции).
- «Накрутчики» стека (20 % пула, 4–6 выдуманных навыков) занимают 51 % топ-10 у поиска по ключевым словам и 23 % у движка (базовая доля в пуле 20 %).

## Что именно проверяется

Критерий 1 ТЗ: «доля релевантных кандидатов в топе выдачи на тестовом наборе пар «вакансия – кандидат»». Мы генерируем рынок, где у каждого кандидата есть **скрытая истина** (реальная специализация, грейд, компетентность, навыки, отраслевой опыт), а платформа видит только **зашумлённые наблюдения** — те же, что и в продукте: подтверждённый тестом грейд и балл, заявленный стек, текст опыта, результаты ФСП. Эталонная релевантность пары считается только по скрытым атрибутам, поэтому система не может «подсмотреть» ответ.

Модель шума наблюдений (параметры зафиксированы в `SyntheticMarket.kt`):

- грейд по тесту совпадает с истинным с вероятностью 0,85, иначе ошибается на одну ступень;
- балл теста = 35 + 55·q + N(0; 9²), где q — скрытая компетентность;
- заявленный стек: истинный навык указан с вероятностью 0,9; 50 % кандидатов честные, 30 % добавляют 1–2 выдуманных навыка, 20 % — «накрутчики» с 4–6 выдуманными популярными навыками;
- самооценка грейда завышена на ступень у 25 % кандидатов;
- текст опыта на русском: истинные навыки упомянуты с вероятностью 0,75, выдуманные — 0,2, отрасли — 0,85; 8 % оставляют поле пустым;
- история ФСП есть с вероятностью 0,10 + 0,45·q (у большинства её нет), места лучше при большей q;
- последняя активность — равномерно 0–400 дней назад и **не связана** с релевантностью (фактор актуальности здесь — чистый шум).

## Эталонная разметка

`u = соответствиеГрейда × (0,45·q + 0,40·покрытиеСтека + 0,15·отрасль)`, 0 при другой специализации; соответствие грейда: тот же 1,0, на ступень выше 0,7, ниже 0,3, на две ступени 0.
Метка: 3 при u ≥ 0,62; 2 при u ≥ 0,45; 1 при u ≥ 0,28; иначе 0. **Релевантный = метка ≥ 2.** Формула эталона намеренно отличается от формулы движка: в ней нет балла теста, ФСП, текста и заявленного стека — только скрытая истина.

## Сравниваемые системы

- **Подбор по потребности (движок платформы)** — Категорийный фильтр (специализация + подтверждённый грейд) и релевантность: тест 30, текст 25, стек 20, ФСП 15, отрасль 5, актуальность 5.
- **Категория + сила профиля (режим банка)** — Точная категория, порядок по силе подтверждённого профиля: 65·тест + 25·ФСП + 10·актуальность. Описание потребности не используется.
- **Только балл теста** — Тот же категорийный фильтр, что у движка, сортировка только по баллу теста.
- **Ключевые слова + заявленный стек («как на обычных площадках»)** — Фильтр по заявленному (самооценённому) грейду; ранг = доля стека вакансии в заявленном стеке + 0,5·доля ключевых слов вакансии в резюме. Тест и ФСП не используются.
- **Случайный порядок внутри категории** — Только категорийный фильтр (специализация + подтверждённый грейд), порядок случайный (среднее по 50 перестановкам).
- **Случайный порядок по специализации** — Только специализация, порядок случайный (среднее по 50 перестановкам).

## Ограничения

- Эталон синтетический: результат показывает, что движок правильно использует сигналы **при наших допущениях** о шуме (тест информативнее самоописания, ФСП коррелирует с компетентностью). Если на реальном рынке допущения неверны, числа будут другими.
- Генератор и движок написаны одной командой; чтобы снизить подгонку, веса заданы заранее, а отчёт построен на рынках, не использованных при разработке. Анализ чувствительности показывает, насколько вывод зависит от весов.
- Тексты опыта собраны из шаблонов, поэтому TF-IDF здесь проще, чем на реальных резюме; вклад текста на реальных данных может отличаться в обе стороны.
- Метрики считаются по всему пулу, а не по выборке; опция «показывать грейд ниже» в отчёте выключена.
- Вес ФСП (15) на синтетике не помогает: без ФСП nDCG@10 меняется на +0,013 [0,002; 0,024]. В генераторе история ФСП — редкий и шумный признак компетентности. Вес сохранён осознанно: ТЗ требует поднимать внутри категории кандидатов с подтверждёнными достижениями ФСП, и это единственный сигнал, независимый от нашего теста. Калибровать его нужно на реальной обратной связи работодателей.
- Уменьшение веса текста вдвое меняет nDCG@10 на +0,015: на шаблонных синтетических текстах информативность TF-IDF ограничена. Мы не меняли веса по отчётным рынкам — это была бы подгонка под тест.

## Как провести такую же оценку на реальных данных

1. Зафиксировать версию движка, пул согласившихся кандидатов (обезличенный), 20–30 реальных потребностей работодателей и `k` (5 и 10) **до** разметки.
2. Для каждой потребности отдать на разметку не только топ движка, но и случайную выборку остальных кандидатов категории (иначе нерелевантность неразмеченных неизвестна); перемешать порядок и скрыть источник.
3. Не менее двух независимых экспертов-нанимающих (тимлиды/HR из отрасли) ставят метку 0–3 по той же шкале; согласованность — взвешенная каппа Коэна, расхождения разбирает третий эксперт.
4. Посчитать P@5/P@10, nDCG@10, MRR с бутстрэп-ДИ по потребностям, сравнить с теми же базовыми линиями (ключевые слова, только тест, случайный порядок) и абляциями — этот код (`RankingMetrics.kt`) переиспользуется без изменений: достаточно заменить синтетические метки на экспертные.
5. Онлайн-метрики после запуска: доля принятых приглашений по позиции в выдаче, время до первого приглашения, доля откликов «не подходит» — и периодическое переобучение весов (learning-to-rank) на этой обратной связи с контролем смещения позиции.
